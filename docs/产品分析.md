# 片刻产品分析：哪里还不够符合直觉

2026-10-25，基于 `personal` 分支当前工作区，含未提交改动。

## 方法

分析框架取自几份公开的产品与体验审查提示词，取它们共同的做法：

- 先写清目标用户和他要完成的任务，再沿任务走流程，不按页面罗列问题（UX Advantage 的 UX audit prompt）。
- 每条发现都给证据和出处，分清亲眼看到的现象与对用户的推测；没有真实用户数据时，推测单独列为待验证问题（product.inc 的 UX audit skill）。
- 用 Nielsen 十条可用性原则做检查清单：系统状态可见、贴近用户的说法、用户可控可撤销、一致性、预防出错、认出而非回忆、效率、简洁、帮助用户从错误中恢复、帮助文档。
- 最后给修改顺序和验收方式，只提建议，不改代码。

证据来源有两种。**源码**：读了 `app/src/renderer` 全部页面和 `backend/pianke/flows` 的回访、推荐逻辑。**实测**：把 `~/Library/Application Support/Pianke` 的数据复制到临时目录，用项目自带的界面驱动脚本跑了一遍，截图存在 `docs/screenshots/pm-review/`。你的真实数据没有被改动。

没覆盖到的：推荐运行中的页面和访谈对话需要调用模型，这次没有触发；本机模型模式没有实测，你的设置是 OpenAI 兼容接口。

## 用户与任务

片刻的用户是有固定口味、不想刷信息流的人。他打开片刻只为一件事：**今晚这一小时，不纠结地决定看什么、读什么、听什么，看完觉得值。**

围绕这件事有三个循环，下面按循环组织发现：

1. **决定**：说一句状态，拿到三部，选一部去看。
2. **回来**：看完或没看，告诉片刻，花的力气越少越好。
3. **变准**：片刻的口味画像随记录变准，用户能看懂、能纠正。

## 一句话结论

视觉和单页细节已经很细，**不直觉的地方集中在动作的命名和流向上**：推荐页最常用的动作“就看这部”和“先存着”没有直接的按钮，存进片单的东西不会再被推荐用到，“还没顾上”的效果和字面相反。这几处改好，三个循环就闭合了。

## 发现

严重程度是估计：4 阻断任务，3 明显绕路或误解，2 小摩擦，1 观感。

### 一、决定

#### F1 推荐结果页缺“就看这部”，“想看”藏在“没看”里　严重 3

**现象**：每部推荐下只有两个按钮：蓝色的“看过了”和灰色的“没看”（`screens/Tonight.tsx:533`、`:538`）。用户刚拿到推荐时最可能做的事是挑一部去看，或者存一部以后看，这两件事都没有直接入口：

- 想存起来，要点“没看”，再在原因里选“想看，先存着”，再点“记下”，三步，而且入口叫“没看”。片单的空状态文案也只能这样教用户（`screens/Shelf.tsx` 片单空状态）。
- “看过了”有两种理解：以前就看过，或者刚按推荐看完。记录面板只好再加一组“按推荐看的 / 以前就看过”来区分（`components/LogPanel.tsx` 的 `askOrigin`），说明标签本身没说清。

**连带后果**：因为没有“选了这部”的信号，第二天回访只能猜。回访逻辑是：最近一晚三部都没动过，就把三部都问一遍（`backend/pianke/flows/feedback.py:210-220`）。用户一晚只看一部，第二天却被问三次“看了吗”。

**建议**：把动作按意图拆开，正面的放前面：

| 按钮 | 效果 |
| --- | --- |
| 就看这部 | 标记为今晚的选择，第二天只问这一部；同时可以打开外部链接 |
| 先存着 | 一步进片单 |
| 看过了 | 只表示以前就看过，直接打分 |
| 不想看 | 展开原因：不感兴趣、不对胃口、今晚不合适 |

“没看”面板里去掉“想看，先存着”，原因选中即提交，不再需要第二次点“记下”。

**验收**：从拿到推荐到把一部放进片单只需一次点击；选了“就看这部”后，第二天回访只出现这一部。

#### F2 等待一分半，期间不能取消，也不知道还要多久　严重 2

**现象**：你最近一次音乐推荐用时 92.6 秒（截图 `a12-past-rec.png` 底部）。运行页只在出错时出现“返回”（`screens/Tonight.tsx:236`），正常运行时没有取消，也没有预计时长。运行状态其实按书架保存在 `App.tsx` 里，切去别的书架再回来不会丢，但界面没告诉用户这一点。

**建议**：运行页加“取消”；按最近几次的耗时给一个预计时间；告诉用户可以先去别处，好了会在侧栏这个书架旁亮一个点。决赛要现场演示，这一分半也是风险，演示时最好走本机模型或预热好的路径。

### 二、回来

#### F3 “还没顾上”的效果是“别再问了”　严重 3

**现象**：回访卡片上的“还没顾上”听起来是“过几天再问我”，点下去后显示“好，不再追问”，并且永久不再问这一部（`components/CheckinCard.tsx` 中 dismiss 分支，后端 `dismiss_checkin`）。字面和效果相反。

**建议**：二选一。改名为“别再问了”；或者保留“还没顾上”，让它真的推迟几天再问，到了回访期限后自动消失。后者更贴合这个按钮被点下时的心情。

**验收**：用户读按钮文字就能说对点下去会发生什么。

#### F4 片单是一条只进不出的路　严重 3

**现象**：

- 推荐流程没有读片单，`backend/pianke/flows/recommend.py` 里没有用到状态为 want 的记录。用户存了十部想看的，问“今晚看什么”时片刻并不考虑它们。
- 片单页只能“看完了”或删除，不能手动添加。朋友推荐的、刚在别处看到的片，没有地方放。
- 补记一部看过的，要进书架，切到“看过”标签，点“补记一部”，再搜，路径偏深。

**建议**：

- 推荐页加一个选项“从片单里挑”，或者在定方向时把片单作为候选来源之一，推荐理由里写明“这部在你的片单里”。
- 片单页加“添加”，复用补记的搜索框。
- 全局加 ⌘K：搜一个作品名，结果上直接给“看过了”“先存着”两个动作。

#### F5 删除没有撤销　严重 2

**现象**：片单行上的 ✕ 直接删除（`screens/Shelf.tsx:159`、`:259`），画像条目的 ✕ 也直接删除（`screens/ProfilePage.tsx:195`）。记录页的删除有二次确认，两处不一致。

**建议**：统一改成删除后底部出现几秒的“已移除，撤销”，比二次确认少一步，也不会误删。

### 三、变准

#### F6 口味画像要用户手动整理　严重 2

**现象**：新记录不会自动进画像。画像页提示“有 1 条新记录还没整理进画像”（截图 `a08-profile.png`），侧栏要攒到 3 条才亮点（`components/Sidebar.tsx` 中 `status.stale >= 3`）。用户需要先理解“记录”和“画像”是两层，再记得回来点“现在整理”。推荐用的却是画像，所以刚写的评语对下一次推荐可能没有作用，用户看不到这层原因。

**建议**：整理改为后台自动进行，时机可以是空闲时、或攒够几条后。整理完在侧栏亮点，画像页顶部写“这次新增了两条，去掉了一条”，并把变化的条目高亮。手动按钮保留在页面上，作为“立即整理”。

#### F7 工程信息混在用户界面里　严重 2

**现象**：

- 侧栏底部两行模型状态显示为“g　cpa.128-1-48-248.sslip.io”（截图 `a01-film-compose.png`）。模型名被截成一个字母，右边是接口域名，两行完全一样，普通用户读不出含义。
- 画像页写“读入 5,214 个 token”“gemini-3.8-flash-high 会把全部记录完整读一遍”；推荐页底部写模型全名和接口域名；设置页有读入速度柱状图。

这些是给评委看的端侧证据，对日常使用是噪音，而且接口模式下域名会占据最显眼的位置。

**建议**：侧栏底部只留一个状态点和一个词：“本机”或“远程接口”，悬停再看细节。token、模型名、速度图收进设置里的“模型”分区。比赛需要展示时，加一个演示模式开关，打开后恢复现在的细节。推荐页底部保留一句隐私说明即可。

### 四、第一次打开

#### F8 第一次推荐来得太晚，进度点也不准　严重 2

**现象**：从打开到第一次推荐要经过：开场动画、隐私说明、名字、选书架、每个书架一面封面墙、四五个问题的访谈、整理画像，七屏左右。名字页写“大概三分钟”。底部进度点画了 5 个，只在第 1 到 3 步显示，到封面墙就消失了（`screens/Onboarding.tsx` 底部 `onboard-dots`），用户不知道还剩多少。

**建议**：封面墙之后直接整理画像并给出第一次推荐，访谈改为推荐页上的一张可选卡片，“多聊两句，推荐会更准”。冷启动的信息量主要来自封面墙上的点选，访谈可以在用户已经尝到甜头后再做。进度点要么覆盖全程，要么去掉。

#### F9 封面墙“点两下是不喜欢”难以发现　严重 2

**现象**：点一次喜欢，第二次不喜欢，第三次清空（`components/CoverWall.tsx` 的 `tap`）。标题只问“哪些片你看过、而且喜欢”，说明文字里的“点两下是不喜欢”很容易略过。想标喜欢却手快多点一下，就变成了不喜欢（截图 `b06-wall-marked.png`）。

**建议**：点一下是喜欢；鼠标移上去时封面角上出现一个小 ✕，点它是不喜欢。两种状态各有一个看得见的入口，不靠记规则。

### 五、导航与一致性

#### F10 再点一次当前位置会清空结果　严重 1

**现象**：在推荐结果页，再点一次侧栏的当前书架，或再点一次“推荐”标签，结果页会换成空白输入页（`App.tsx:173`、`screens/DomainView.tsx:58`）。结果能从“最近的推荐”找回，但这个行为没有提示，和“换个说法”按钮重复。

**建议**：点击当前位置不做任何事，回到输入页只通过“换个说法”或 ⌘N。

#### F11 “最近的推荐”只记得作品名　严重 1

**现象**：侧栏每条历史显示三部作品名和日期，如“偷拐抢骗、布达佩斯大…　10月5日”（截图 `a01-film-compose.png`）。用户回想时更可能记得当时的情境，“加班那天晚上”，而不是片名。

**建议**：第二行显示当时说的话或选的标签，日期放到悬停里。

## 做得好的，应该保留

- **只给三部，并且说清为什么**：推荐理由下面引用用户自己说过的原话，并注明出自哪一部（截图 `a12-past-rec.png`）。这是片刻和流媒体推荐最直观的差别。
- **“没看”的原因分流**：每个原因写到不同的地方，选中后马上告诉用户这次选择的效果（`components/PassPanel.tsx` 的 `EFFECT_NOTE`）。用户知道自己的点击在影响什么。
- **画像可读、可改、有依据**：每条结论下面列出依据的作品，用户改过的条目会标“你改过”并永久保留。
- **核实过程摊开给用户看**：查不到的作品明确写“片库里没有，不用它”，建立信任。
- **隐私说明跟着模式变**：切到远程接口后，引导页和输入框下的说明都会改口，没有夸大本机处理。

## 需要找真人验证的问题

这些是推测，专家走查回答不了，需要找三五个真实用户各用一周：

1. 书和专辑也一次推三部是否合适。一本书要读几周，用户可能更想要一本，外加一本备选。
2. 用户是否注意到并在意“书影音之间”的跨书架推断，还是只把它当三个独立工具。
3. 看完后愿意写评语的比例。如果大多数人只打星，画像整理的输入会比设计时设想的单薄。
4. 第二天回访是一种提醒还是一种打扰，尤其是音乐两天、书两周的不同节奏。

## 建议的修改顺序

1. **F1 与 F3 一起改**：两者共用“选了哪一部”这个信号。先加“就看这部”和“先存着”，再按新信号收窄回访、修正“还没顾上”。改动在 `Tonight.tsx`、`PassPanel.tsx`、`CheckinCard.tsx` 和 `feedback.py` 的回访逻辑。
2. **F7、F10、F5**：改动小，立刻让界面更安静、更可控，决赛演示前做完。
3. **F4**：片单进入推荐、片单可添加、⌘K 快速记录。需要动推荐管线，工作量最大。
4. **F6**：后台自动整理，需要考虑本机模式下整理占用内存和用户正在推荐时的冲突。
5. **F8、F9、F2、F11**：首次引导与等待体验。F8 改动会影响演示脚本，安排在比赛结束后做也可以。

每项改完，可以用 `app/scripts/drive/` 下的驱动脚本重放对应流程并截图，对照每条发现里的验收标准检查。
